# 元AI跨端排障记录

本文记录截至 2026-08-18 在 Web、Mobile、Desktop、后端与 CI 联调中已复现的问题、根因和
解决方案。它不包含账号、密码、API Key、令牌或上传文件 URL；凭据只能存放在被 Git
忽略的本地 `.env` 文件。

## 工具链与运行环境

| 问题                                                                          | 根因                                                             | 解决方法                                                                                                                                                          |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Husky 在提交时使用了与项目不一致的 pnpm，导致 `node_modules` 兼容性报错。     | 终端 `PATH` 优先解析到宿主 pnpm，而仓库锁定了 `pnpm@10.22.0`。   | Hook 和手工命令均通过 `corepack pnpm` 使用 `package.json` 中锁定的版本。                                                                                          |
| 安装新依赖后 `pnpm-lock.yaml` 被大范围重排，`turbo@latest` 也发生了无关漂移。 | 使用了不匹配的 pnpm 版本重算整份 lockfile。                      | 从提交基线保留必要依赖解析，使用 `corepack pnpm install --frozen-lockfile` 验证；不要提交无关格式化或版本漂移。                                                   |
| Docker 镜像更新后是否需要删除旧容器不明确。                                   | Compose 不会自动替换与新配置不一致的已存在容器。                 | 先运行 `docker compose ps -a` 核对实际容器；存在差异时使用 Compose 仅重建受影响服务，不手工删除卷。镜像始终使用完整版本加 digest。                                |
| `pnpm dev:real` 或桌面启动无法直接验证真实后端。                              | 根脚本和桌面脚本缺少统一入口，或开发服务器变量被外部宿主注入。   | 只通过仓库 `package.json` scripts 启动；桌面开发脚本清除继承的 renderer 地址，后端、Web、Electron 使用同一经校验的 API 地址。                                     |
| 直接调用宿主的 pnpm 后开发命令与提交钩子表现不一致。                          | 外层 pnpm 主版本高于仓库锁定版本，解析出的依赖和锁文件格式不同。 | 先由 Corepack 解析 `packageManager`，再运行根或 workspace 的 package script；不要用全局 pnpm 重写 lockfile。                                                      |
| 新开发机因 Node.js/pnpm 版本漂移而安装或启动失败。                            | 仅使用宽松的版本范围，且没有可执行的启动前检查。                 | 仓库固定 Node.js `22.21.1`、pnpm `10.22.0`、Turbo `2.10.7`，提供 `.nvmrc`、`.node-version`、Volta 元数据和 `pnpm check:runtime`；初始化、开发和打包入口均先验证。 |

## 真实界面与桌面端

| 问题                                                              | 根因                                                        | 解决方法                                                                                                    |
| ----------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Electron 开发窗口显示空白或 Vite 404。                            | 宿主注入的 `ELECTRON_RENDERER_URL` 指向被占用或错误的端口。 | 通过 `scripts/dev-desktop.mjs` 清除该变量并使用桌面自身 Vite 地址；真实窗口验证必须从 package script 启动。 |
| 打包 renderer 使用 `file://` 时，API、SSE、上传会遭到 CORS 限制。 | 后端只允许浏览器开发源，且 `file://` 没有安全可控 origin。  | 使用受限 `yuanai-app://` renderer 协议，后端仅白名单允许实际 Web/桌面源；深链接仍保持独立协议。             |
| 登录窗口新增二维码入口后出现纵向滚动条。                          | 原固定高度只容纳账号密码登录表单。                          | 登录窗口高度提升到 680px，并在 Electron 真窗口中确认二维码与全部操作均可见。                                |
| 认证或其他短提示占用表单布局。                                    | 页面内联错误提示会推动表单内容。                            | 使用右上角 Toast，自动消失；真实注册页确认提示不挤占操作区。                                                |

## 文件与预览

| 问题                                                      | 根因                                                         | 解决方法                                                                                                                                                                    |
| --------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 上传成功但模型没有获得文件内容。                          | 历史消息构建只传文字，或选择了不支持视觉输入的纯文本模型。   | 后端对 PNG/JPEG/WebP/GIF、PDF、TXT/MD、JSON/CSV、DOCX/XLSX 提取受限上下文；图片作为视觉块传递，文本和表格作为清洗文本传递。模型不支持图片时，在发送前明确提示并阻止该请求。 |
| 初版“预览”只是下载链接或文本占位，体验与聊天应用不一致。  | 文件元数据和预览界面未按类型设计。                           | Web 使用右侧 Artifact 面板；Desktop 在单独受限窗口显示预览；Mobile 调用系统/原生查看器。未知类型仍可上传和下载，但不宣称可解析。                                            |
| 附件直到 AI 回复后才可见。                                | 流式状态没有携带乐观附件。                                   | 在用户消息乐观占位中立即显示附件，流完成后由服务端消息替换。                                                                                                                |
| 宽图、长图和多图预览对齐不稳定，不能连续查看。            | 预览卡没有固定媒体边界，也将非图片混入图片导航。             | 约束媒体容器尺寸；图片 lightbox 支持滚轮缩放 25%-400%，只在图片附件之间左右切换，切换文本或文档时退出放大模式。                                                             |
| Firefox 点击“下载源文件”在窗口中打开内容。                | 直接导航到可内联响应的 URL。                                 | 使用鉴权请求取得 Blob，设置 `download`，并延迟回收 Blob URL 以兼容 Firefox。                                                                                                |
| Mobile 图片附件没有可点击预览，文件图标又与其他端不一致。 | 移动端把所有附件都当作普通下载项，图标未按 MIME/扩展名统一。 | 图片进入原生图片预览器，其他支持类型交给系统文档查看器；附件元数据统一使用共享的 MIME/扩展名映射，未知类型仍只提供下载。                                                    |

## 语音输入

| 问题                                       | 根因                                                                        | 解决方法                                                                                                                                                 |
| ------------------------------------------ | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 浏览器授权后转写接口返回 HTTP 422。        | API client 为 multipart 请求强行写入 JSON `Content-Type`，破坏了 boundary。 | 仅对 JSON 请求设置该 header，让 `FormData` 由运行时生成 multipart boundary。                                                                             |
| 桌面录音经常报告“无法读取音频时长”。       | 某些浏览器生成的 WebM container 不带可用 duration metadata。                | 后端先读容器时长，缺失时回退 `ffprobe` 音频包时间戳；仍限制 MIME、体积和最大时长。                                                                       |
| 桌面端媒体权限使用 Electron 原生阻塞弹窗。 | 直接调用系统 message box 无法满足应用内焦点、可访问性和一致性要求。         | 改为受信任 preload IPC 触发的应用内允许/拒绝对话框，含焦点回收、Tab 限制、Escape 拒绝和超时。后续禁止为应用流程使用原生权限弹窗。                        |
| 未配置转写服务时用户只看到“暂不可用”。     | Whisper/第三方服务没有可用的 API Key。                                      | 采用 AssemblyAI Pre-recorded STT：本地 `.env` 仅存 `ASSEMBLYAI_API_KEY`，`.env.example` 只保留空占位；接口对未配置、超时和 provider 失败返回可理解错误。 |
| 录音 UI 停止后自动发送或移动端无法停录。   | 识别状态和发送状态耦合，停止事件未正确收敛。                                | 三端仅把转写文本插入草稿；移动端将 listener、录音资源与取消路径都显式清理。                                                                              |

## 模型、搜索与真实 API

| 问题                                                                 | 根因                                                                        | 解决方法                                                                                                                                                                                                                  |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 模型选择器只显示旧的纯文本模型，Agnes 能力和 DeepSeek 元数据未生效。 | 后端模型目录、前端过滤和运行时 API 结果不一致。                             | 模型目录统一由后端公开；Agnes 2.5 Flash 为聊天/视觉模型，Agnes Image/Video 仅供媒体任务，DeepSeek V4 Flash/Pro 保持纯文本能力。                                                                                           |
| 点击“联网搜索”快捷入口没有开启实际开关。                             | 快捷入口只填充了文案，没有更新 composer 状态。                              | 快捷入口同时设置 `enableWebSearch=true`，并由消息发送体携带此设置。                                                                                                                                                       |
| 本地浏览器从 `127.0.0.1` 调用真实 API 失败。                         | CORS 只允许 `localhost`。                                                   | 后端开发白名单同时包含 `localhost` 与 `127.0.0.1`；生产环境使用明确 HTTPS origin。                                                                                                                                        |
| 使用 mock 通过但真实后端失败。                                       | mock 没有覆盖认证、CORS、流式和存储契约。                                   | 每个跨端能力除单元测试外，都在 `pnpm dev:real` 或对应应用 script 下进行真实 API 和真实界面验证。                                                                                                                          |
| 联网搜索不可用或提示没有 provider。                                  | SearXNG 容器未启动，或 `SEARCH_PROVIDER` 指向了未配置 Key 的 Brave/Tavily。 | 默认执行 `pnpm setup:search && docker compose up -d searxng` 使用无密钥 SearXNG；选择 Brave/Tavily 时分别填写 `BRAVE_SEARCH_API_KEY` / `TAVILY_API_KEY`。代理仅在确有需要时显式设置 `SEARXNG_PROXY_URL`，不假设固定端口。 |
| 搜索来源在哪里查看。                                                 | 来源被设计为思考内容的一部分，而非回答正文。                                | 展开回答下方的思考块，再展开联网搜索工具条目即可查看标题、摘要和安全链接；折叠时不占正文空间。                                                                                                                            |
| 桌面端滚动后已展开的思考或 `search_web` 详情重新折叠。               | `react-virtuoso` 回收历史消息行，组件内局部状态随卸载丢失。                 | 虚拟列表按消息 ID 保存思考状态、按工具调用 ID 保存详情状态；`<details>` 受控渲染，回到该消息时恢复用户选择。                                                                                                              |

## 会话状态与数据库迁移

| 问题                                               | 根因                                                                                        | 解决方法                                                                                                                                               |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 切换会话后模型又恢复为默认值。                     | 模型选择只写入本地 composer 状态，没有持久化到会话或在重新进入会话时恢复。                  | 模型选择立即 PATCH 当前会话；会话列表/详情是唯一服务端真相，三端在 active conversation 改变时按其 `model` 同步 composer。                              |
| 关闭当前“思考”开关后，以前消息的思考内容也消失。   | 渲染逻辑把历史消息可见性错误地绑定到当前输入框开关。                                        | 开关只决定新请求的 `enable_thinking`；历史消息只要持久化了 `thinkingContent` 或 thinking part，就始终渲染并可折叠查看。                                |
| 用户两次输入相同问题，被错误归并为同一个回答版本。 | 版本分组按用户文本相等推断，忽略了它们可能是两轮独立请求。                                  | 仅在请求显式带 `regeneratedFromMessageId` 时形成版本组；正常消息保持该字段为空，即使文本完全相同也显示为独立轮次。                                     |
| Agnes 2.5 Flash 在未开启思考时仍返回推理内容。     | 请求没有传递该模型文档规定的 thinking 参数。                                                | Agnes 流式请求传入 `extra_body={"chat_template_kwargs": {"enable_thinking": <当前轮开关>}}`；存量思考内容不受这个新请求参数影响。                      |
| Firefox 报跨域而 `/messages` 实际返回 500。        | 新增列的 Alembic migration 未在本地数据库执行，异常响应没有走到正常 CORS 处理，掩盖了根因。 | 先检查后端日志和 `uv run alembic current`，执行 `uv run alembic upgrade head` 后重试；将迁移检查纳入真实 API 启动前步骤，不把 500 当作 CORS 配置问题。 |

## 扫码登录与 Android 真机

| 问题                                                          | 根因                                                              | 解决方法                                                                                                                             |
| ------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 二维码曾携带长期凭据或复用后仍被接受。                        | 设备间登录把 token 放入码内容会泄露认证信息，且缺少单次消费状态。 | 二维码仅包含挑战 ID 和 API 地址；后端存储 challenge/poll secret 哈希，批准后签发一次性 authorization code，成功交换后标记 consumed。 |
| Android 扫码后一直显示“正在确认”，虽然 Web 已经登录。         | 手机本地批准请求与目标端消费存在竞态，UI 未重新读取最终状态。     | 在批准后 750ms 重新检查挑战；状态为 `approved` 或 `consumed` 即返回聊天。                                                            |
| 登录成功后再次点击扫码仍展示旧的已批准、已拒绝或过期页面。    | Expo Router 复用了上一扫描实例和 route state。                    | 侧栏操作创建新的 `session` 参数强制重挂 scanner，关闭/成功均 `router.replace('/(main)/chat')`，下次进入始终打开相机。                |
| Web 刷新二维码时页面上下跳动，或长期显示“正在准备二维码”。    | QR 状态区没有稳定高度，刷新失败和倒计时状态没有统一回收。         | 状态容器保持最小高度，刷新动作独立布局；挑战创建、轮询、过期和限流都有明确状态及刷新入口。                                           |
| 手机上的 `exp://127.0.0.1:8081` 无法连接。                    | `127.0.0.1` 指向手机自身，不是开发电脑。                          | 手机与电脑连接同一 Wi-Fi，使用电脑局域网 IP：`http://<LAN-IP>:8000/api/v1`；启动 Expo LAN 地址后由 Expo Go 扫码。必要时放行防火墙。  |
| Expo/Metro 看不到文件更新或 Android 构建受 JDK/网络影响失败。 | Linux inotify watch 限制过低、JDK 路径或网络代理未配置。          | 提升 `fs.inotify.max_user_watches`；使用本机 JDK 17；网络受限时确认代理端口后再下载。不要把代理或本机路径写入源码。                  |

## 验证和提交规则

- 单元测试不能替代真实界面验证：Web、Desktop、Mobile 每项用户可见功能都要用对应
  `package.json` script 启动后手工检查；真机流程需要连接设备时先提示用户。
- 每个独立功能在相关单元/集成测试通过后单独创建本地 Conventional Commit，不推送也
  不合并到 `dev`，除非用户明确授权。
- `.codex/` 仅保存本地计划、截图和进度，不进入 Git；`docs/` 可由执行会话维护，记录
  应描述真实验证边界和仍未解决的外部限制。

| Linux/Windows Electron 构建在产物完成后报 `GitHub Personal Access Token is not set`。 | Desktop `package.json` 声明了 GitHub publisher，tag 构建会让每个矩阵 job 自己尝试发布；这些 job 没有发布权限，也不应重复创建 Release。 | 构建命令追加 `--publish never`，由最后拥有 `contents: write` 的 `softprops/action-gh-release` job 统一发布。     |
| macOS 构建报 `/Users/runner/work/yuanai/yuanai/apps/desktop not a file`。             | workflow 给非 Windows 平台注入空的 `CSC_LINK`；Electron Builder 将空值解析为当前 app 目录路径。                                        | 将桌面步骤拆为签名 Windows 与无签名 Linux/macOS；macOS 不再注入 Windows 证书的空值，同时使用 `--publish never`。 |
| Linux/macOS 仍显示 `artifacts will be published if draft release exists`。            | workflow 通过 pnpm 参数转发 `-- --publish never`，桌面 package script 最终把额外的 `--` 传给 Electron Builder，未可靠关闭发布检测。    | 将 `--publish never` 固定写入 `apps/desktop/package.json` 的所有 package script，workflow 只调用 script 名称。   |
| Android EAS 云构建报 Node `v20.19.2`、pnpm `9.15.5` 不满足项目固定版本。              | EAS 免费云构建镜像的运行时低于项目所需 Node `22.21.1`、pnpm `10.22.0`，且队列时间不可控。                                              | 移除 Android Actions/EAS Release job；只使用本机 Gradle release 构建，再用 GitHub CLI 上传 APK。                 |
| 单独重跑 Web/桌面 job 后 Release 没有对应新产物。                                     | 旧 workflow 仅上传临时 artifact，等待所有 job 成功后才由最终 publish job 创建 Release。                                                | prepare job 先建立 Release 并从提交信息生成描述；Web 与每个桌面矩阵 job 构建成功后直接上传并覆盖同名资产。       |

这些问题均发生在 GitHub Actions 的发布构建边界，不是应用运行时代码错误。修复后应使用
Release workflow 的 `workflow_dispatch`，填写已有 tag `v0.1.0`、更新后的 `master` commit，
并选择 `all` 重新构建；不要移动或覆盖已有 tag。
