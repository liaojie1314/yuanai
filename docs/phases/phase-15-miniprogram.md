# Phase 15 - 小程序端

- **前置条件**：后端 API 与 SSE 协议稳定；已完成域名备案与 HTTPS（见 `docs/deployment.md`）
- **建议分支**：`feat/phase-15-miniprogram`
- **执行范围**：Taro 小程序端，按平台能力**尽可能完整迁移**现有功能
- **阶段定位**：`CLAUDE.md` 中「微信小程序为二期计划」的落地阶段

---

## 1. 产品目标

1. 在小程序内完成登录、会话管理、流式对话、多模态输入等**平台允许的全部核心功能**
2. 与 Web/Mobile/Desktop 共用同一账号与会话，微信身份绑定到既有 yuanai 账号
3. 一套 Taro 代码可扩展到支付宝/抖音小程序，不为单一平台锁死

### 1.1 范围原则

用户要求「能在小程序上实现使用的功能都迁移过去」。因此本阶段**不做功能取舍清单**，
而是做**能力矩阵**（§4）：默认全部迁移，只有被平台硬性限制挡住的才不做，且必须写明原因。
平台能力放开后，被挡住的项应重新评估。

### 1.2 非目标

- 不在小程序内实现独立的模型调用、审批判定或记忆存储（一律走后端）
- 不做需要动态执行代码的能力（平台禁止，见 §4）
- 不做小程序端的执行节点（无本地文件与进程能力）

---

## 2. 技术选型

| 项   | 选择                      | 理由                                            |
| ---- | ------------------------- | ----------------------------------------------- |
| 框架 | Taro（React）             | 与仓库 React 技术栈一致，`packages/core` 可复用 |
| 位置 | `apps/miniprogram`        | 与三端同级                                      |
| 首发 | 微信小程序                | 其余平台（支付宝/抖音）复用同一套 Taro 代码     |
| 复用 | `packages/core` + `types` | 业务逻辑、类型；UI 需另写（§3）                 |

### 2.1 packages/ui 不能复用

`packages/ui` 基于 shadcn/ui + Tailwind + DOM，小程序没有 DOM，组件必须用 Taro 组件
（`View`/`Text`/`ScrollView`）重写。这与 Mobile 端的处理一致：**共享业务逻辑，不共享 UI**。

`packages/core` 的复用同样受限于其浏览器耦合点，处理方式与 Phase 14 §2.1 相同：
token 持久化改注入 `Taro.setStorageSync` 实现，网络层改注入 Taro 请求实现。

---

## 3. 流式对话：小程序没有 EventSource

这是本阶段最大的技术点。小程序不支持 `EventSource`，浏览器 `fetch` 流式读取也不可用。

方案：使用**分段传输**（微信 `wx.request` 的 `enableChunked: true`，Taro 透传），
后端 SSE 端点无需改造，客户端自行解析 `text/event-stream` 分帧。

- 复用 `AGENTS.md` 十约定的事件协议，未知事件类型静默忽略
- 分段回调返回 `ArrayBuffer`，需自行处理**半个事件跨块到达**的粘包/拆包
- 断线重连复用既有重放语义，不另设一套
- 若目标平台不支持分段传输，降级为 WebSocket 通道；**不降级为轮询**

## 4. 能力迁移矩阵

| 能力                        | 状态 | 说明                                                                           |
| --------------------------- | ---- | ------------------------------------------------------------------------------ |
| 登录 / 账号绑定             | ✅   | `wx.login` 换 code，后端绑定到既有账号（§5）                                   |
| 会话管理                    | ✅   | 完全复用后端 API                                                               |
| 流式对话                    | ✅   | 分段传输方案（§3）                                                             |
| Markdown 渲染               | ✅   | 需小程序专用渲染组件，不能用 `react-markdown`                                  |
| 代码高亮                    | ✅   | 需轻量方案，注意主包体积（§6）                                                 |
| 图片 / 文件上传             | ✅   | `chooseMedia` / `chooseMessageFile` + `uploadFile`，走既有分片接口             |
| 语音输入                    | ✅   | `RecorderManager` 录音上传转写，复用 Phase 11 STT 链路                         |
| 模型切换 / 设置             | ✅   | 完全复用后端 API                                                               |
| 记忆 / 知识库 / Skills 管理 | ✅   | 纯 CRUD 界面，无平台限制                                                       |
| 自动化管理                  | ✅   | 同上                                                                           |
| 助手形象（静态）            | ✅   | 静态立绘，与 Mobile 首版一致                                                   |
| 助手形象（2D 动画）         | 🟡   | Canvas/WebGL 可行但吃包体与性能，首版降级为静态（同 Mobile）                   |
| 实时语音对话                | 🟡   | 需 `<live-pusher>`/`<live-player>` + 实时音视频服务，不能用裸 WebRTC；单独评估 |
| 视频通话 / 视觉理解         | 🟡   | 摄像头可取帧，但实时链路同上受限；Phase 13 能力按平台方案另行评估              |
| Artifact 查看               | 🟡   | 文本/图片可看；HTML 类 Artifact 无法沙箱渲染，降级为下载或跳转                 |
| 屏幕共享                    | ❌   | 平台无此能力                                                                   |
| 执行节点                    | ❌   | 无本地文件与进程能力                                                           |
| 第三方 Skill 动态执行       | ❌   | 平台禁止动态执行代码，且违反审核规则                                           |
| 桌面通知 / 后台常驻         | ❌   | 无后台运行能力；改用订阅消息（§5.2）                                           |

## 5. 账号与消息

### 5.1 身份绑定

- `wx.login` 取 code → 后端换 openid/unionid → **绑定到已有 yuanai 账号**
- 绑定必须由已登录用户发起，或走完整注册流程，**不允许微信身份直接创建影子账号**
- 一个 yuanai 账号可绑定多个渠道身份，解绑不影响主账号
- 复用 Phase 12 §7.4 的渠道绑定模型，不另建一套

### 5.2 订阅消息

小程序无后台常驻，长任务完成通知走微信订阅消息：

- 必须用户显式订阅，且遵守平台的一次性订阅规则
- 通知只带标题与跳转，**不在通知内容中携带对话正文或私密记忆**
- 用户可随时退订，退订后不再下发

---

## 6. 包体积

微信主包上限 2MB、总包 20MB，是硬约束：

- 主包只放登录与对话主流程
- 记忆/知识库/Skills/自动化等管理界面走**分包加载**
- Markdown、代码高亮等重依赖按需分包，不进主包
- 构建产物体积纳入 CI 检查，超阈值即失败

---

## 7. 合规与审核

小程序的上线门槛不在技术侧，**必须前置确认**：

- 小程序需完成备案与类目选择；AI 对话类目通常要求相应资质
- 生成式 AI 服务在境内提供需满足《生成式人工智能服务管理暂行办法》相关要求，
  可能涉及算法备案 —— **这是产品准入问题，不是工程问题，需提前确认**
- 用户可见的生成内容需接入内容安全检查（如 `msgSecCheck`）
- 服务器域名必须在小程序后台白名单内，且为 HTTPS、不可用 IP
  （与 `docs/deployment.md` 的备案要求一致）
- 用户输入与 AI 输出均需过内容安全，违规内容不展示且留审计记录

---

## 8. 测试要求

- 分段传输的粘包/拆包：半个事件跨块到达时解析正确
- 断线重连后事件不重复、不丢失
- 未知 SSE 事件类型被静默忽略
- 主包体积不超过平台上限（CI 校验）
- 微信身份无法直接创建账号（只能绑定）
- 订阅消息内容不含对话正文
- 上传走既有分片接口，大文件可续传
- 内容安全检查失败时不展示内容且有审计记录

---

## 9. 验收标准

- 登录 → 绑定 → 会话 → 流式对话 → 多模态输入的完整链路在真机跑通，有实测记录
- §4 标 ✅ 的能力全部落地；标 🟡/❌ 的在文档中有明确平台原因
- 主包体积在限制内且有 CI 门禁
- 小程序端无独立的模型调用、审批判定或记忆存储实现
- 合规项（备案、类目、资质、内容安全）在提审前逐项确认完毕
