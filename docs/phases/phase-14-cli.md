# Phase 14 - 终端 TUI 与本地执行节点

- **前置条件**：Phase 6 执行节点协议（配对、challenge、本地审批、ACK、撤销）已稳定
- **建议分支**：`feat/phase-14-cli`
- **执行范围**：`apps/cli` 终端 TUI、本地执行节点接入、凭证安全存储、TUI 内审批
- **阶段定位**：让开发者在终端里用同一个助理，并把**自己的开发机**变成助理可用的执行节点

---

## 1. 产品目标

1. 在终端提供**全屏交互界面**（TUI）完成登录、会话管理、流式对话与 Artifact 查看
2. 把执行 TUI 的这台机器注册为 Phase 6 执行节点，让 Agent 能在本机真实跑工具
3. 审批以模态形式出现在 TUI 内，高风险动作不绕过确认
4. 与 Web/Desktop/Mobile 共用同一账号、同一会话、同一记忆 —— 不产生第二套身份体系

### 1.1 关于 Hermes

Hermes Agent 是本阶段的**参考形态**（CLI + Gateway + 单机安装），但 Phase 5 D7 已决定
**不 fork Hermes 产品**。因此：

- 命令名为 `yuanai`，不叫 `hermes`，避免与上游产品混淆
- 不引入 Hermes 的 SQLite/FTS5 本地真相源、配置文件体系与本机密钥模型
- 后端仍是唯一真相源，CLI 只是又一个 API 客户端
- 借鉴其 CLI 交互形态与「代码调用工具」思路（后者见 Phase 10 §4）

### 1.2 非目标

- 不做非交互 / CI 模式（`--json`、退出码驱动）—— 无人值守下的高风险动作授权需要独立设计，
  留待后续阶段
- 不做本地模型推理
- 不做离线模式：无网络时 CLI 不可用，不维护本地会话副本
- 不在 CLI 内实现独立的工具注册表或审批策略，一律复用后端策略

## 2. 技术选型

| 项       | 选择                               | 理由                                                  |
| -------- | ---------------------------------- | ----------------------------------------------------- |
| 语言     | TypeScript                         | 与仓库同构，`packages/core` 可直接复用                |
| 位置     | `apps/cli`                         | monorepo 内，与三端同级                               |
| 运行时   | Node 22（与仓库固定版本一致）      | 复用 `.nvmrc` / `engines` 约束                        |
| TUI 框架 | Ink（React for terminal）          | 用 React 写终端界面，与仓库技术栈一致，可直接用 hooks |
| 分发     | npm 全局安装起步                   | 单二进制打包（Node SEA）留作后续优化，不是首版门槛    |
| 复用     | `packages/core` + `packages/types` | apiClient、SSE 解析、token 刷新拦截器、共享类型       |

选 Ink 而不是 blessed/Ratatui 类方案，是因为它让 TUI 复用与 Web 端同样的 React 心智与
`packages/core` 的 hooks；终端渲染的差异集中在组件层，业务层不必写第二遍。

### 2.1 packages/core 的 Node 兼容性

`packages/core` 按铁律**不得引入平台专用 API**，这正好让 CLI 可以复用它。但两处与浏览器
环境耦合的行为必须抽象掉，否则 CLI 无法工作：

| 耦合点       | 现状（浏览器） | CLI 需要                          |
| ------------ | -------------- | --------------------------------- |
| token 持久化 | `localStorage` | OS 钥匙串 / 受限权限文件（见 §4） |
| 流式传输     | 浏览器 `fetch` | Node `fetch`（Node 22 原生可用）  |

处理方式：在 `packages/core` 暴露**存储适配接口**，由各端注入实现。
这属于既有抽象的补齐，不是为 CLI 新增平台分支。

## 3. 形态：默认 TUI，子命令兜底

```bash
yuanai                            # 默认进入全屏 TUI
yuanai login | logout | whoami    # 无需 TUI 的一次性命令
yuanai -m "一句话提问"             # 单轮提问后退出，纯文本输出
yuanai node run                   # 前台常驻执行节点（行模式，便于放进 systemd/tmux）
yuanai node register | status | unregister
```

原则：**交互走 TUI，脚本与自动化走子命令**。子命令不是 TUI 的退化版，而是明确服务于
「不需要界面」的场景（登录、注册节点、常驻执行）。

### 3.1 TUI 布局

```
┌────────────┬──────────────────────────────────────────────┐
│ 会话列表   │ 消息区（流式渲染、Markdown、代码块）          │
│ (可折叠)   │                                              │
│            ├──────────────────────────────────────────────┤
│            │ 输入区（多行、历史、斜杠命令）                │
├────────────┴──────────────────────────────────────────────┤
│ 状态栏：助理 / 模型 / 节点状态 / 待审批数                  │
└───────────────────────────────────────────────────────────┘
```

审批以**模态覆盖层**出现，抢占焦点并暂停输入区，避免用户在不知情时继续打字。

### 3.2 交互约定

- 斜杠命令在输入区内触发（`/new`、`/model`、`/assistant`、`/approve`、`/quit`）
- `Ctrl+C` 取消当前流式生成，**不退出程序**；连按两次或 `/quit` 才退出
- `Esc` 关闭模态或折叠面板
- 上下键翻输入历史，`Ctrl+R` 反向搜索
- 所有阻塞操作显示进度，不出现无反馈的静默等待

### 3.3 渲染约束

终端不是浏览器，以下约束必须在实现时遵守：

- 流式输出**按块重绘而非整屏重绘**，否则长会话会闪烁并吃满 CPU
- 消息区虚拟化：只渲染可视区域，历史消息按需加载
- 终端宽度变化时重排，不假设固定宽度
- 颜色按终端能力降级（truecolor → 256 → 无色），不依赖颜色传达唯一信息
- 非 UTF-8 终端降级为 ASCII 边框与符号
- 窗口过窄时自动折叠会话列表，保证消息区可读

### 3.4 非 TTY 降级

管道、重定向、CI 等无 TTY 场景下**不启动 TUI**：

- 自动切换为行模式，输出纯文本，不含 ANSI 控制符与动画
- 高风险审批一律拒绝（见 §5.2）

## 4. 凭证安全

CLI 持有长期 refresh token，是整个体系里最容易被忽视的攻击面。

- **优先使用操作系统钥匙串**（macOS Keychain / Windows 凭据管理器 / Linux Secret Service）
- 钥匙串不可用时降级为权限受限文件（`0600`，放 XDG 配置目录），
  且**必须显式告知用户降级**，不静默写明文
- 任何情况下不把 token 写进 shell 历史、日志、崩溃报告或 `--verbose` 输出
- 支持 `yuanai logout` 彻底清除本地凭证与节点私钥
- 节点私钥与访问 token **分开存储**，撤销节点不需要重新登录

## 5. 本地执行节点

CLI 的核心价值在这一节：让 Agent 在开发者本机真实执行工具。

### 5.1 复用而非重写协议

Phase 6 的执行节点客户端目前实现在 `apps/desktop/src/main/execution-node/`。CLI 需要完全
相同的配对、challenge 签名、任务重投、ACK 与撤销语义。**重写第二份实现必然产生行为漂移**，
而这些语义正是安全边界所在。

因此：把协议客户端抽取为平台中立的共享包，Desktop 与 CLI 各自只注入平台相关的
密钥存储与审批 UI。抽取过程**不得改变协议行为**，Desktop 现有的执行节点 E2E 必须继续通过 ——
这是抽取正确性的判据。

### 5.2 TUI 内审批

- 低风险（只读）动作按后端策略自动执行
- 高风险动作弹出**模态覆盖层**，展示工具名、参数摘要、影响范围与剩余超时，并抢占焦点
- 决策是原子的：同一审批只能被决定一次，重复决定返回既有结果
- **无 TTY 时（管道、后台、无交互终端）高风险动作一律拒绝**，不做默认放行 ——
  这是 §1.2 不做 CI 模式的直接后果，宁可拒绝也不静默授权
- `yuanai node run` 作为常驻进程运行时同样适用：无人值守下不自动放行高风险动作
- 审批超时按后端策略处理，TUI 不自行延长

### 5.3 文件访问边界

- 节点只能访问用户显式授权的路径，沿用 Phase 6 的先授权后访问模型
- 授权范围在 `yuanai node register` 时声明，可随时收窄
- 未授权路径的读取请求被拒绝并回报给 Agent，不静默返回空

## 6. 与 Web/Desktop 的一致性

| 项           | 要求                                                  |
| ------------ | ----------------------------------------------------- |
| 账号与会话   | 同一账号、同一会话列表，CLI 建的会话在 Web 立即可见   |
| 记忆         | 复用 Phase 7 记忆，按 `assistant_id` 隔离，CLI 不另存 |
| 模型路由     | 经后端 `ai_service.py`，CLI 不直连任何 AI 供应商      |
| 审批策略     | 后端统一下发，CLI 不本地放宽                          |
| SSE 事件协议 | 与 `AGENTS.md` 十的事件约定一致，未知事件类型静默忽略 |

## 7. 测试要求

- 登录后 token 落在钥匙串；钥匙串不可用时降级路径有显式提示
- `--verbose` 与日志输出中不出现 token（正则断言）
- 协议客户端抽取后，Desktop 执行节点 E2E **仍然全绿**（抽取正确性判据）
- 无 TTY 环境下不启动 TUI，输出不含 ANSI 控制符
- 无 TTY 环境下高风险审批被拒绝，且拒绝原因明确
- 同一审批重复决定返回既有结果（幂等）
- 未授权路径读取被拒绝
- TUI 组件用 Ink 测试渲染器断言：流式增量只重绘消息块、终端缩窄时会话列表折叠、
  无色终端下不丢失信息
- `Ctrl+C` 取消生成但不退出程序
- CLI 创建的会话在后端可见（集成测试）

---

## 8. 验收标准

- 在终端完成登录 → TUI 对话 → 注册节点 → 接收任务 → 模态审批 → 真实执行的完整链路，有实测记录
- 协议客户端抽取后 Desktop 与 CLI 行为一致，两端 E2E 均通过
- 凭证不以明文出现在任何日志、历史或输出中
- 无交互环境下不存在任何高风险动作的自动放行路径
- 长会话下流式渲染不闪烁、CPU 占用稳定，有实测数据
- CLI 不包含独立的模型调用、审批判定或记忆存储实现
