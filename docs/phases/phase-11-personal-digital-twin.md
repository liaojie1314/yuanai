# Phase 11 - 个人数字孪生、目标系统与主动助理

- **前置条件**：Phase 10 L3 有界自治达到成功率、安全和成本门禁
- **建议分支**：`feat/phase-11-personal-digital-twin`
- **执行范围**：个人上下文图、目标/承诺系统、信号检测、模拟决策、主动建议和驾驶舱
- **阶段定位**：从“等待用户下命令”升级为“理解生活与工作全局，并在正确时间提供可执行帮助”

---

## 1. 产品愿景

个人数字孪生不是复制用户人格，也不是让 AI 替用户决定人生。它是一个可解释、可校正、可删除的动态上下文模型：

- 用户想实现什么
- 正在承担哪些承诺
- 时间、注意力和预算如何分配
- 哪些项目、人物、资料和事件相互关联
- 实际执行结果与计划有何偏差

助理基于这个模型发现冲突、遗漏、风险和机会，再提出可执行建议。目标仍由用户设定，重大决定仍由用户作出。

### 1.1 与普通长期记忆的区别

| 长期记忆             | 个人数字孪生                           |
| -------------------- | -------------------------------------- |
| 记住孤立事实和偏好   | 表达目标、实体、承诺、资源和事件的关系 |
| 主要用于回答更个性化 | 用于持续规划、检测变化和衡量进展       |
| 检索驱动             | 事件驱动 + 时间驱动 + 约束推理         |
| 多为文本片段         | 结构化状态、时间线、来源和不确定性     |

### 1.2 非目标

- 不推断或诊断用户的疾病、心理状态、政治立场等敏感属性
- 不以“提高效率”为名评价用户的人生价值
- 不自行创建长期目标、财务承诺或社会关系动作
- 不把相关性当因果性，不做无依据的预测
- 不构建不可见的广告画像或出售用户画像

## 2. Context Graph

### 2.1 实体

- Person：用户、家人、朋友、同事、客户
- Organization：学校、公司、社区和服务机构
- Goal：生活、学习、职业、创作和经营目标
- Commitment：会议、承诺、截止日期、订阅和定期事项
- Project / Task：执行结构
- Resource：文件、知识、账号、预算和设备
- Event：邮件、日历、Run、交易资料、里程碑和外部变化
- Metric：用户明确选择跟踪的指标
- Decision：重要选择、依据、假设和复盘结果

### 2.2 关系

- belongs_to、depends_on、blocks、supports、conflicts_with
- owns、assigned_to、related_to、communicated_with
- derived_from、measured_by、decided_by、supersedes

每条边保存来源、置信度、有效期和可见空间。推断关系与用户确认关系必须明显区分。

### 2.3 存储

首版继续使用 PostgreSQL：

- `context_entities`
- `context_relations`
- `context_observations`
- `context_snapshots`

常用关系查询通过递归 CTE 和物化视图完成。只有当图遍历、规模或实时推理证明 PostgreSQL 不足时才引入图数据库。

## 3. 事件与状态

### 3.1 Observation

所有变化先记录为 Observation，不直接改“用户真相”：

- 来源：用户输入、连接器事件、Agent Run、文件、人工确认
- 观察时间与事件发生时间
- 结构化 payload、来源引用和敏感级别
- 置信度和解析版本

Projector 将 Observation 投影为当前 Context State；解析器升级后可以重建投影。

### 3.2 Snapshot

按日/周或关键决策生成快照：

- 当前活跃目标与承诺
- 资源/时间分配
- 阻塞与风险
- 指标状态
- 重要关系变化

Snapshot 不是向量摘要，而是可比较的结构化状态，用于趋势和复盘。

## 4. 目标系统

### 4.1 Goal Contract

目标至少包含：

- 用户原话和可选的结构化描述
- 为什么重要（可选，用户控制）
- 成功标准和“不做什么”
- 时间范围与检查频率
- 允许使用的数据、工具和预算
- 主动程度与通知策略
- 暂停/完成/放弃条件

### 4.2 从目标到行动

```text
Long-term Goal
 -> Milestones
 -> Projects
 -> Tasks / Automations
 -> Agent Runs / Human Actions
 -> Outcomes
 -> Review
```

Agent 可以建议结构，但用户可随时编辑。目标改变后，相关自动化不会静默继承新权限。

### 4.3 多目标冲突

系统只指出事实约束和可见冲突，例如时间重叠、预算超限、依赖缺失。价值取舍交给用户，不把模型偏好伪装成最优解。

## 5. 信号引擎

### 5.1 信号类型

- Deadline Risk：按剩余工作、依赖和可用时间判断风险
- Commitment Conflict：日程、承诺、任务或预算冲突
- Stalled Goal：一段时间无进展且有明确下一步
- Opportunity：与活跃目标直接相关的新资料或事件
- Anomaly：用户选择跟踪的指标发生显著变化
- Forgotten Follow-up：用户明确承诺但尚未完成
- Automation Drift：自动化连续失败或产出质量下降

### 5.2 Signal 不是 Notification

Signal 先进入排序与合并：

```text
价值 = 与目标相关度 x 时间紧迫度 x 可行动性 x 置信度
       - 打扰成本 - 重复度 - 敏感风险
```

只有超过用户阈值且存在明确行动建议才通知；其余进入“今日建议”或周复盘。

### 5.3 反馈闭环

用户可标记有用、无用、错误、太频繁、无需再提醒。反馈调整规则权重，但不自动改变安全策略。

## 6. 主动助理模式

### 6.1 模式

- Quiet：只有明确提醒、审批和严重风险
- Balanced：每日少量高价值建议，默认
- Proactive：对选定目标持续监控和提出任务

模式可按空间和目标设置，不提供全局“完全接管”。

### 6.2 主动任务边界

无需额外确认即可：

- 刷新只读信息
- 在私有工作区生成草稿、报告和候选计划
- 运行用户已启用、风险上限符合的自动化

仍需确认：

- 新增长期监控范围
- 对外通信和共享内容
- 改变第三方系统状态
- 扩大预算、工具、数据或收件人作用域

## 6.5 助手形象与表现

给 [Phase 7 §8.5](./phase-7-memory-skills-automation.md) 的人格配上可见、可听的外在表现。
**形象只是表现层**：它不改变能力、不改变权限、不参与决策。

### 6.5.1 交付范围

| 做                                             | 不做                           |
| ---------------------------------------------- | ------------------------------ |
| 静态形象（用户上传 或 站内 AI 生成）           | 3D 模型与实时驱动              |
| TTS 音色选择（从供应商预置音色中选）           | 声音克隆 / 复刻他人声音        |
| 2D 动画表情（Live2D 或序列帧）：待机/说话/思考 | 全身动作捕捉、口型精确对齐音素 |
| Web / Desktop 渲染                             | Mobile 首版动画（降级为静态）  |

不做声音克隆是**产品决定也是合规决定**：复刻真人声音涉及肖像声音权与诈骗风险，
超出个人助理的必要范围。

### 6.5.2 数据模型

- `assistant_appearances`：`assistant_id`、形象类型（static / live2d / sprite）、
  静态立绘与头像的文件引用、动画资源包引用、缩放与锚点、主题色
- `assistant_voices`：`assistant_id`、TTS 供应商、音色 ID、语速语调、是否默认开启朗读
- 资源文件走已有的文件存储（`avatars/` 前缀），不新建存储通道

### 6.5.3 形象来源与审核

三种来源，都必须过同一道内容检查：

1. **预置形象库**：站内提供若干风格化默认形象，开箱即用
2. **用户上传**：需通过图片内容审核；**禁止上传真实人物照片作为助手形象**
3. **AI 生成**：复用 Phase 6 的图片生成能力，按提示词生成立绘

审核要求：

- 上传与生成结果都要过安全审核，拒绝色情、暴力、政治敏感与真人肖像
- 拒绝时给出明确原因，不静默失败
- 资源文件大小与分辨率有上限，超限先压缩再入库

### 6.5.4 动画与状态映射

2D 动画只需要四个状态，不做复杂表演：

| 状态 | 触发                    | 表现          |
| ---- | ----------------------- | ------------- |
| 待机 | 无任务                  | 轻微呼吸/眨眼 |
| 思考 | Run 进行中              | 思考姿态      |
| 说话 | 流式输出中 / TTS 播放中 | 口型循环      |
| 提醒 | 有待审批或主动建议      | 轻量吸引注意  |

约束：

- 口型**不做音素级对齐**，仅在说话期间循环，成本与收益不成正比
- 动画必须可**一键关闭**，关闭后回落为静态立绘，且不再加载动画运行时
- 尊重系统"减少动态效果"（`prefers-reduced-motion`）设置，自动降级为静态

### 6.5.5 性能与降级

形象**不得影响对话主流程**：

- 动画资源**懒加载**，首屏不阻塞；加载失败静默降级为静态立绘，不报错打断对话
- 渲染在独立图层，掉帧不得影响消息流式渲染
- 低端设备与低电量模式自动降级为静态
- Mobile 首版只渲染静态立绘与头像，不引入 2D 运行时，避免包体与内存代价
- 形象渲染库按需加载，不进入主包

### 6.5.6 语音输出

- 音色从 TTS 供应商预置列表中选择，落库只存音色 ID 与参数，不存音频模型
- 朗读**默认关闭**，由用户显式开启
- 长回复只朗读摘要或用户选中段落，不整段硬念
- 朗读可随时中断；中断后动画状态同步回落到待机

### 6.5.7 隐私

- 形象与音色属于用户数据，删除助理时一并删除对应资源
- 形象资源不用于任何模型训练
- 上传的形象文件与普通附件同权限：不公开、不可被其他用户枚举

### 6.5.8 测试要求

- 动画关闭后不加载动画运行时（打包与运行时都要验证）
- 动画资源加载失败时降级为静态且对话不中断
- `prefers-reduced-motion` 生效
- 真人照片上传被拒绝
- 删除助理后形象与音色资源确实清除
- Mobile 端不打包 2D 运行时

### 6.5.9 验收标准

- 形象与音色的任何异常都不会中断或拖慢对话主流程，有测试证据
- 关闭动画后无额外资源加载与性能开销
- 形象内容审核对三种来源一致生效
- 形象层无法影响助理的能力、权限或输出内容的安全边界

## 6.6 实时语音对话

§6.5.6 的朗读是「把已生成的文本念出来」，本节是**全双工语音对话**：用户说话、助理边听边想边答，
可随时打断。视频（摄像头视觉理解、屏幕共享）不在本阶段，见 Phase 13。

### 6.6.1 交付范围

| 做                                       | 不做                                 |
| ---------------------------------------- | ------------------------------------ |
| 按住说话 / 自由说话两种模式              | 声音克隆、用户音色复刻               |
| 流式 STT → LLM → 流式 TTS 的自组流水线   | 直接采用厂商端到端 Realtime 单体接口 |
| 打断（barge-in）与静音检测（VAD）        | 多人会议、说话人分离（diarization）  |
| 与 §6.5 形象状态机联动（待机/思考/说话） | 音素级口型同步                       |
| 通话录制与转写回放（默认关闭）           | 情绪识别、声纹身份认证               |

### 6.6.2 为什么自组流水线而不是厂商 Realtime 单体

厂商端到端 Realtime 接口延迟更低、打断由厂商处理，但会把**模型选择权**一起交出去：
yuanai 的模型路由、配额、审批与记忆注入都在 `ai_service.py`，用单体接口等于绕过这一层。
自组流水线保留了「STT 与 TTS 可换供应商、LLM 仍走既有路由」的自由度，也让国内供应商可用。
代价是端到端延迟更高、打断与 VAD 要自己做，§6.6.5 给出预算。

### 6.6.3 媒体链路与凭证

**媒体面直连供应商，控制面留在后端**：

```
客户端 ──(1) 申请通话凭证──> FastAPI ──(配额/权限校验)──> 签发短期 token
客户端 ──(2) 音频上行─────> STT 供应商（短期 token 直连）
客户端 ──(3) 转写文本─────> FastAPI → ai_service.py → LLM（走既有路由）
客户端 <─(4) 回复文本流─── FastAPI
客户端 ──(5) 合成请求────> TTS 供应商（短期 token 直连）
```

**对「AI 调用必须经 ai_service.py」铁律的例外，范围严格限定在第 2 步与第 5 步**：
STT 与 TTS 是媒体转码服务，不做对话推理。**第 3 步的 LLM 推理没有例外**，
仍必须经 `ai_service.py`，否则模型路由、配额与审批全部失效。

凭证约束：

- token 由后端签发，**单次通话有效、按 scope 限定供应商与用量**，不下发长期密钥到客户端
- 签发即写一条 `voice_sessions` 记录，用于事后对账（直连意味着用量只能事后核对）
- 通话结束或超时后 token 立即失效
- 供应商密钥只存服务端 Secret Store，任何情况下不出现在前端包或日志里

### 6.6.4 数据模型

```
voice_sessions      id, user_id, assistant_id, conversation_id, mode(push_to_talk|open_mic),
                    stt_provider, tts_provider, voice_id, started_at, ended_at,
                    duration_ms, token_cost, audio_seconds, status
voice_turns         id, session_id, role(user|assistant), transcript, confidence,
                    started_at, ended_at, barge_in(bool), audio_object_key(nullable)
```

通话产生的文本轮次**并入所属 `conversation` 的消息流**，不另开一套会话体系 ——
语音只是输入输出形态，不是独立的对话空间。

### 6.6.5 延迟预算与打断

目标：用户停止说话到听见第一个音节 **≤ 1.2s**（P50）、**≤ 2.0s**（P95）。

| 段                 | 预算    | 手段                                |
| ------------------ | ------- | ----------------------------------- |
| VAD 判定说完       | ≤ 300ms | 客户端本地 VAD，不等服务端          |
| STT 尾包到最终文本 | ≤ 300ms | 流式 STT，边说边出中间结果          |
| LLM 首 token       | ≤ 500ms | 复用现有 SSE 流；系统提示与记忆预热 |
| TTS 首音频块       | ≤ 300ms | 流式 TTS，按句切分，首句优先        |

打断（barge-in）规则：

- 检测到用户开始说话，**立即停止 TTS 播放并取消未播放的合成请求**
- 已播出的内容按实际播出长度截断后写入 `voice_turns`，不记录用户没听到的部分
- 打断后 LLM 若仍在生成，取消该次生成，不把废弃输出写进消息流
- 形象状态同步回落到「聆听」

### 6.6.6 用户体验

- 语音入口在对话界面内，**默认关闭**，开启需一次显式授权（麦克风权限）
- 麦克风状态必须有持续可见的指示，不允许静默录音
- 实时显示用户侧转写文本，用户能看到「助理听成了什么」
- 网络抖动或供应商不可用时降级为普通文字对话并提示，不静默失败
- 支持随时切回文字；切换不丢失对话上下文

### 6.6.7 录制与回放

- **默认不录音**，仅保留文本转写；录制需用户显式开启且每次通话都有可见提示
- 开启后音频落 MinIO，与普通附件同权限（不公开、不可被他人枚举）
- 提供按通话删除与按时间批量删除；删除同时清除对象存储与 `voice_turns.audio_object_key`
- 音频与转写不用于任何模型训练

### 6.6.8 平台范围

| 端      | 首版                                     |
| ------- | ---------------------------------------- |
| Web     | ✅ 完整（WebRTC / MediaRecorder）        |
| Desktop | ✅ 完整                                  |
| Mobile  | ✅ 语音，形象降级为静态立绘（见 §6.5.5） |

### 6.6.9 测试要求

- 打断后 TTS 在 200ms 内停止播放，且废弃内容不进消息流
- 通话凭证过期后无法继续调用供应商
- 凭证 scope 被篡改（换供应商 / 超时长）时后端拒绝签发
- 供应商不可用时降级为文字对话，对话不中断
- 未开启录制时不产生任何音频对象
- 删除通话后音频对象确实从存储中消失
- LLM 推理路径仍经 `ai_service.py`（用替身断言，防止被改成直连）

### 6.6.10 验收标准

- 首音节延迟 P50 ≤ 1.2s、P95 ≤ 2.0s，有实测数据
- 打断在真实设备上稳定生效，不出现「助理说完才停」
- 直连例外只覆盖 STT/TTS，LLM 直连会被测试拦住
- 任何语音异常都不影响文字对话主流程
- 麦克风状态始终可见，无静默录音路径

## 7. 决策支持与模拟

### 7.1 Scenario

用户可以提出“如果……会怎样”：

- 调整项目优先级后的时间影响
- 不同旅行/采购方案的预算和约束
- 不同学习计划的负荷
- OPC 不同内容/客户投入方案的资源影响

模拟使用隔离 Scenario，不修改真实 Goal、Task、Calendar 或自动化。

### 7.2 假设透明

每个模拟结果必须列出：

- 已知事实和来源
- 用户输入的假设
- 模型补充的假设
- 不确定因素
- 可验证的下一步

### 7.3 专业领域限制

健康、法律、税务、投资等输出必须区分资料整理、一般信息和专业建议。系统不自动执行治疗、申报、投资交易等动作。

## 8. 驾驶舱

### 8.1 普通用户视图

- 今天最重要的 1-3 项
- 等待用户决定/完成的事项
- 活跃目标和下一里程碑
- 即将发生的冲突/风险
- 最近完成和节省的时间
- “为什么显示这条”与关闭入口

### 8.2 空间视图

- 生活：日程、家庭事项、旅行/购物计划
- 学习：课程、进度、复习和资料
- 工作：项目、会议、交付物和团队承诺
- 创作者：内容管线和素材
- OPC：客户、交付、内容、经营资料和风险

### 8.3 时间线

统一展示用户事件、Agent Run、外部变化、决策和目标状态。时间线支持按空间和敏感级别过滤，不提供跨用户全局搜索。

---

## 9. 隐私与用户控制

### 9.1 可见与可编辑

- 用户能查看系统认为有哪些实体、关系和活跃目标
- 推断关系明确标记，可确认、修改或拒绝
- 每个 Signal 显示使用的数据和规则
- 支持按空间暂停 Context Graph 投影

### 9.2 私密模式

用户可发起“不保存、不记忆、不进入数字孪生”的临时任务；该模式仍保留最小安全审计元数据，但不保存内容。

### 9.3 删除

删除实体时展示依赖影响：相关记忆、关系、自动化和索引。用户可选择仅断开关系或连同来源派生数据删除。

## 10. 技术组件

```text
Connector Events / Runs / User Input
            |
      Observation Store
            |
      Context Projectors
            |
   PostgreSQL Context Graph
       /            \
Signal Engine     Snapshot Engine
       |              |
Ranking/Policy    Review/Simulation
       \              /
        Today / Workspace Dashboard
```

Projector、Signal Rule 和 Ranking Model 全部版本化。每条 Signal 保存生成版本，便于解释和回放。

## 11. 评测

### 11.1 数据正确性

- Observation 去重与乱序事件
- 关系有效期和 supersede
- 连接器撤销后的投影清理
- 推断事实不会覆盖用户确认事实

### 11.2 主动质量

- Precision of proactive suggestions
- 用户完成率、忽略率、关闭率和负反馈率
- 每日打扰数量和重复率
- 错误冲突/截止风险率
- 从 Signal 到实际行动的时间

### 11.3 安全

- 敏感属性推断禁止用例
- 跨空间/跨租户关系泄漏
- 恶意连接器事件造成记忆/上下文投毒
- 自动化通过目标变化扩大权限
- 模拟 Scenario 意外写入真实系统

---

## 12. 验收标准

- [ ] 用户能查看并校正 Context Graph 中与自己有关的关键实体和关系
- [ ] 目标、承诺、任务、Run 和结果形成可回溯链路
- [ ] 系统能发现真实日程/任务冲突并给出可执行建议
- [ ] 主动建议满足打扰预算，低价值建议不会泛滥
- [ ] Scenario 模拟与真实数据严格隔离
- [ ] 用户修改长期目标不会自动扩大已有权限
- [ ] 私密模式内容不进入记忆、知识库、评测和数字孪生
- [ ] 敏感推断、跨空间泄漏和 Context 投毒安全测试通过
- [ ] 真实用户认为主动建议“有用”而不是“多余”的比例达到产品阈值

**进入 Phase 12 的许可证**：主动建议在真实灰度中达到准确率和打扰阈值，Context Graph 可解释、可校正、可删除，并且没有产生不可接受的敏感推断。
