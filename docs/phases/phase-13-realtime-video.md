# Phase 13 - 实时视频对话与视觉理解

- **前置条件**：Phase 11 §6.6 实时语音对话已跑通延迟与打断门禁
- **建议分支**：`feat/phase-13-realtime-video`
- **执行范围**：摄像头视觉理解、屏幕共享、助手侧 2D 画面、通话录制与回放
- **阶段定位**：把「能听会说」扩展为「能看」，让助理在用户的真实画面与屏幕上协助，
  同时不把视频变成一条绕过模型路由与审批的暗管

---

## 1. 产品目标

1. 用户可以在通话中打开摄像头，助理据此理解现场并回答（看实物、看文档、看设备）
2. 用户可以共享屏幕或窗口，助理据此协助操作（看报错、看表格、看设计稿）
3. 助理侧画面复用 Phase 11 §6.5 的 2D 形象，与语音状态同步
4. 通话可录制并回放，且录制默认关闭、全程可见

### 1.1 非目标

- 不做助理侧的真人级视频合成（数字人主播、换脸、口型驱动的真人视频）
- 不做人脸识别、人脸比对与身份认证
- 不做情绪识别与微表情分析
- 不做多人视频会议与说话人分离
- 不做持续常开的环境监控（摄像头只在通话内、用户显式开启时工作）

## 2. 与 Phase 11 的边界

| 能力                      | 归属                  |
| ------------------------- | --------------------- |
| 音频上下行、STT/TTS、打断 | Phase 11 §6.6         |
| 通话会话与文本轮次模型    | Phase 11 §6.6.4       |

| 视频采集、抽帧、视觉理解  | 本阶段                |

视频**不新开会话体系**：复用 `voice_sessions`，增加视频相关字段与帧记录表。

---

## 3. 媒体链路：视频帧不走直连

Phase 11 §6.6.3 给了 STT/TTS 直连供应商的例外，**该例外不延伸到视频**。

原因很直接：STT/TTS 是媒体转码，而**视觉理解是模型推理**。多模态模型调用与文本对话调用
是同一类行为，必须受同一套模型路由、配额、审批与记忆策略约束，因此：

```
客户端 ──采集视频──> 客户端本地抽帧与压缩
       ──抽样帧────> FastAPI ──> ai_service.py ──> 多模态模型
       <──理解结果── FastAPI
```

- 视频**原始流不上传**，只上传按策略抽样并压缩后的帧
- 帧调用与文本调用共用同一配额账本，不另开口子
- 禁止前端直接把帧发给任何模型供应商

---

## 4. 抽帧策略

全帧率送多模态模型在成本与延迟上都不可行，抽帧策略是本阶段的核心工程问题。

| 场景               | 采样策略                                       |
| ------------------ | ---------------------------------------------- |
| 默认（摄像头常开） | 低频心跳采样，≤ 0.2 fps（约 5s 一帧）          |
| 用户提问时         | 立即取当前帧，作为该轮问题的视觉上下文         |
| 画面显著变化       | 本地帧差检测触发补采，设上限避免抖动刷屏       |
| 屏幕共享           | 仅在用户提问或画面显著变化时采样，不做心跳采样 |

约束：

- 抽帧与帧差检测在**客户端本地**完成，未被采样的帧不出设备
- 单轮对话送入模型的帧数设硬上限，超出时保留最近与变化最大的帧
- 每帧压缩到模型可接受的最小分辨率，不传原始分辨率
- 采样频率与上限可配置，且必须对用户可见（见 §6）

---

## 5. 屏幕共享与敏感内容

屏幕共享比摄像头风险高得多：密码管理器、私信、财务数据都可能出现在画面里。

- 共享前必须明确提示「助理将看到你共享的内容」，并让用户选择**窗口**而非整屏（默认窗口）
- 共享期间保持显著的常驻指示，且指示不可被页面内容遮挡
- 用户可随时一键停止共享；停止后立即丢弃未发送的帧
- 检测到疑似凭证输入界面时暂停采样并提示（尽力而为，不承诺完全识别）
- 屏幕帧与摄像头帧同权限存储，不公开、不可被他人枚举

**渠道隔离**：跨渠道机器人（Phase 12 §7）**不得**发起或接收视频通话，
屏幕内容不允许流向任何第三方渠道。

---

## 6. 用户体验与可见性

- 摄像头与屏幕共享**默认关闭**，各自需要独立的显式授权，不共用一次授权
- 采集状态必须持续可见：摄像头开启、共享进行中、本轮送了几帧
- 提供「本次通话助理看到了什么」的回看入口，列出实际送出的帧
- 弱网时自动降低采样频率并提示，不静默降级
- 关闭视频后通话继续以语音进行，不中断

---

## 7. 数据模型

```
voice_sessions      （Phase 11 §6.6.4 已有）新增：
                    video_enabled(bool), screen_share_enabled(bool),
                    frames_sent(int), video_object_key(nullable)

vision_frames       id, session_id, turn_id(nullable), source(camera|screen),
                    captured_at, width, height, bytes, reason(heartbeat|question|change),
                    object_key(nullable), model_call_id(nullable)
```

`vision_frames` 默认**只存元数据不存图像**；仅在用户开启录制时写 `object_key`。

---

## 8. 录制与回放

- 视频录制**默认关闭**，且与音频录制是**两个独立开关**
- 录制期间全程可见提示，任何参与方都能看出正在录制
- 录制文件落 MinIO，与普通附件同权限
- 回放同时展示：视频轨、转写文本、该时刻实际送模型的帧
- 支持按通话删除与按时间批量删除，删除同时清除对象存储、`vision_frames.object_key`
  与 `voice_sessions.video_object_key`
- 视频、帧与转写**不用于任何模型训练**

## 9. 平台范围

| 端      | 摄像头 | 屏幕共享           | 助理侧 2D 形象 |
| ------- | ------ | ------------------ | -------------- |
| Web     | ✅     | ✅                 | ✅             |
| Desktop | ✅     | ✅（系统级选择器） | ✅             |
| Mobile  | ✅     | ⬜ 首版不做        | 静态立绘       |

Desktop 的屏幕共享必须走系统原生选择器授权，与 Phase 6 执行节点的文件授权模型一致：
**先授权、后访问，不做隐式全屏抓取**。

---

## 10. 成本控制

视觉理解按帧计费，是本阶段最容易失控的成本点：

- 每用户每日视觉帧配额，超出后停止采样并提示（不静默继续烧钱）
- 通话级帧数上限，防止单次长通话打爆额度
- 配额与文本 token 共用同一账本与告警口径
- 管理侧可按用户/助理查看帧用量

---

## 11. 测试要求

- 视频帧调用走 `ai_service.py`，前端直连供应商的实现会被测试拦住
- 未采样的帧不出设备（抽帧逻辑单测 + 网络层断言）
- 停止共享后不再有帧发出
- 单轮帧数与每日配额上限生效，超限时提示而非静默继续
- 未开启录制时不产生任何视频对象与 `object_key`
- 删除通话后视频对象与帧记录确实消失
- 跨渠道机器人无法发起视频通话
- 关闭视频后语音通话不中断
- Mobile 不打包屏幕共享相关代码

---

## 12. 验收标准

- 摄像头与屏幕共享各自独立授权，且状态全程可见，无隐式采集路径
- 视觉理解调用全部经过既有模型路由与配额，无绕过路径，有测试证据
- 抽帧策略在真实通话中把帧用量控制在预算内，有实测数据
- 录制默认关闭；开启后可完整删除，删除后存储中无残留
- 视频异常（摄像头被占用、共享被系统拒绝、弱网）不影响语音与文字主流程
